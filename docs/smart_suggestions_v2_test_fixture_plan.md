# Smart Suggestions v2 - Test Fixture Plan

## 1. Goal

Plan deterministic Smart Suggestions v2 fixtures so parser behavior and the approval UI can be tested without requiring `OPENAI_API_KEY`.

This is a planning-only block. No fixture files, runtime controls, tests, or app behavior changes are implemented here.

## 2. Why Deterministic Fixtures Are Needed

The approval UI currently needs real V2 records to exercise:

- row selection
- approve action
- reject action
- mark pending action
- blocked-row non-approval behavior
- session-only decision state
- product-switch leakage checks

Without an API key, V2 generation is correctly disabled and the UI shows an empty structured table. That is safe, but it leaves the approval workflow hard to test manually.

Deterministic fixtures solve this by providing stable V2 records that can be used for tests and controlled local demos without calling OpenAI.

## 3. Fixture Coverage

The fixture should include a small set of field-level suggestion records for one demo SKU.

Recommended records:

1. Pending suggestion
   - target field: `description`
   - safe content improvement
   - `approval_status = needs_review`
   - `suggestion_status = review_required`

2. Approved-capable suggestion
   - target field: `product_name`
   - low-risk title improvement
   - enough source fields and reason
   - should be approvable by the user

3. Rejected-capable suggestion
   - target field: `attributes`
   - draft attribute wording
   - should be rejectable by the user

4. Blocked suggestion
   - target field: `ean` or `price`
   - should normalize to `blocked_insufficient_source`
   - must not be approvable

5. High-risk suggestion
   - target field: `warning_notes`
   - risk level high
   - requires human review
   - no legal compliance guarantee

6. Missing source/reason case
   - missing source fields or reason
   - should become blocked after parser normalization

## 4. Fixture Location

Recommended fixture location:

`tests/fixtures/smart_suggestions_v2_demo_response.json`

Why:

- Clearly test/demo-supporting, not product data.
- Keeps it separate from `data/sample_products.csv`.
- Keeps fixture data out of exports unless explicitly loaded for demo/test.
- Works naturally with pytest.

Optional later UI/demo location:

Use the same fixture path from a clearly labeled demo-only control in Streamlit. Do not duplicate fixture content in `app.py`.

## 5. Fixture Type Decision

Recommended approach: both parser unit test fixture and optional Streamlit demo fixture.

### Parser Unit Test Fixture

Use the fixture in `tests/test_suggestion_parser.py` to verify:

- valid records parse consistently
- blocked records remain blocked
- approved-like AI output is downgraded to needs review
- missing source/reason cases become blocked
- unsupported target fields cannot become usable records

### Optional Streamlit Demo Fixture

Add a small future control in the V2 experimental section:

`Load Demo Smart Suggestions v2`

Rules:

- clearly labeled as demo fixture data
- only loads local deterministic records
- does not call OpenAI
- uses the same parser path as real V2 output
- stores results in the same V2 session-state keys
- does not affect exports
- does not update product data

## 6. Avoiding Confusion With Real AI Output

Fixture-loaded output must be clearly marked.

Recommended UI wording:

`Demo fixture loaded. These rows are deterministic test data, not generated by OpenAI.`

Recommended session-state key:

`smart_suggestions_v2_source = "demo_fixture"` or `"openai"`

Display should show the source when records are present:

- `Source: Demo fixture`
- `Source: OpenAI response`

Do not label fixture data as AI-generated.

## 7. Testing Approval UI Without API Key

Future fixture implementation should allow this manual flow without `OPENAI_API_KEY`:

1. Start Streamlit.
2. Open AI Suggestions tab.
3. Expand or click `Load Demo Smart Suggestions v2`.
4. Confirm V2 records appear.
5. Approve an approved-capable row.
6. Reject a rejected-capable row.
7. Confirm blocked row cannot be approved.
8. Confirm pending reset works.
9. Confirm exports do not change.
10. Restart the app and confirm decisions do not persist.

## 8. Keeping Fixtures Separate From Exports and Write-Back

Fixture data must not:

- modify product data
- modify sample products
- update scores
- update issues
- update review tasks
- appear in Management Export
- appear in AI Suggestions v1 export
- create approved-product-data output

In v1, fixture data should only populate the V2 display/session state for testing the V2 approval UI.

## 10. Manual Smoke Test Checklist

After fixture implementation:

1. Run `python -m streamlit run app.py`.
2. Open the AI Suggestions tab.
3. Confirm V1 still appears unchanged.
4. Confirm V2 section appears.
5. Without API key, load demo fixture records.
6. Confirm V2 records appear.
7. Approve one non-blocked row.
8. Reject one non-blocked row.
9. Confirm blocked row cannot be approved.
10. Confirm V2 source is labeled as demo fixture.
11. Confirm exports are unchanged.
12. Restart app and confirm decisions do not persist.

## 11. Rollback Strategy

Keep fixture implementation as one focused commit.

Rollback steps:

1. Revert the fixture commit.
2. Run `python -m pytest`.
3. Run `python -m py_compile app.py`.
4. Start Streamlit manually.
5. Confirm V2 returns to API-key-only generation plus empty safe table when no records exist.

## 12. Explicit Non-Goals

Do not implement in the fixture block:

- approved-only export
- product data write-back
- Management Export V2 integration
- database persistence
- user login or roles
- marketplace presets
- new dependencies
- sample product changes
